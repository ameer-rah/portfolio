3. What's something you spend a lot of time thinking about or working on, in any part of your life? What draws you to it?

I spend a lot of time thinking about what makes a system reliable beneath the abstractions people normally interact with. That curiosity led me to build Mini Redis from scratch rather than only use an existing cache. I wanted to understand how a hash map and linked list support LRU eviction, how TTL behavior changes under concurrent access, and how a server should respond when several clients connect or shut down unexpectedly. I am drawn to this kind of work because each layer reveals another tradeoff between performance, correctness, and simplicity. I enjoy reaching the point where I can explain not only that something works, but why it works and where it can fail.

4. Tell us about a challenge, professional or personal, that stretched you. What did you do, and what did you take away from it?

Building concurrent behavior into Mini Redis stretched me because bugs were not always reproducible and a locally correct operation could still break the shared relationship between the hash map and LRU list. I first reduced the design to a clear invariant: every cached entry had to correspond to exactly one list node, and every operation that changed either structure had to preserve that relationship. I protected the shared state with a single lock, then added stress tests, expiration tests, and live socket integration tests instead of relying on manual checks. I also implemented a bounded worker pool and graceful shutdown so that the server's lifecycle was testable, not just its commands. I took away that difficult systems problems become manageable when I define the invariant, isolate failure modes, and build verification into the design from the beginning.
